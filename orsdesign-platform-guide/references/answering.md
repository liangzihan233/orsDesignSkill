# 回答与补问

## 先判断问题

用户要的是功能介绍、找到入口、配置操作、写代码、解释代码、排错还是验收？结合现有上下文选一种主任务。不要每次先讲完整平台，也不要强迫新手填技术表格。

把自然语言转成可观察行为：“当哪一题怎样回答，哪个目标何时发生什么”。足够明确就给答案。仅当缺失内容改变代码或行为时集中补问：来源和目标题型、真实编码、全部/任意/不含、空答案是否命中、结束还是正常完成。截图看不清编码时明确指出，不根据题目文字猜编码。

## 代码回答

1. 一句话说清应该在哪个入口做。
2. 给准确的界面路径和适用题型／版本；需要替换的编码集中列出。
3. 给可复制代码，不将解释性占位文字混进可运行片段。
4. 用一两句话说明命中行为及未命中行为。
5. 列出最少的测试输入和预期结果，通常包含命中、不命中和未作答。
6. 附实际阅读过的帮助文章链接及验证级别。

如果编码尚未确认，将代码标为“模板”，不能说能直接用于用户问卷。只有问题依赖某个版本差异时才问版本，不让每次提问都变成安装配置问答。

## 证据表述

- “已按版本 X 的入口合同核对”：没有实际运行。
- “编译检查通过”：仅说明语法和入口检查。
- “合成用例运行通过”：说明测试输入、预期和运行器版本，不等同用户问卷通过。
- “平台验收通过”：必须真的检查保存回读和模拟答题结果。

不会联网时说使用随包资料；搜索无结果不代表平台没有该功能。没有依据的 API 明确不确定，不能创造一个看似合理的函数。
